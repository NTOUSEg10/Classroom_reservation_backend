# 專案任務：海大教室借用平台

## 1. 角色與目標

你是一名資深全端開發工程師。請為國立臺灣海洋大學設計並開發一個名為「**海大教室借用平台**」的網頁應用程式，旨在提供全校師生與管理員一個高效、透明且自動化的教室預約與管理系統。

交付順序：**規劃（撰寫 `docs/SPEC.md`）→ 實作 → 測試 → 審查**，詳見第 9 節。

## 3. 技術與架構職責劃分

為避免混淆，請嚴格遵守以下技術選型與職責劃分：

- **前端 (Frontend)**: Svelte (建議搭配 SvelteKit) + Tailwind CSS + TypeScript。
- **後端 (Backend)**: FastAPI + Python + Pydantic，負責核心業務邏輯、權限驗證與 API 提供。
- **資料庫、身分驗證與推播 (BaaS)**: **Supabase 或 Firebase（二擇一）**。請統一使用其中一套服務來負責關聯式資料庫存儲（或 NoSQL）、檔案儲存、使用者身分驗證，以及推播通知。請在 `SPEC.md` 中記錄你的選型理由與取捨。

## 5. 系統需求 (Requirements)

### 功能性需求 (Functional Requirements)

- **FR-001**: 使用者分為系統管理員與借用人。
- **FR-002**: 系統應要求借用人註冊需提供基本資料與聯絡資訊。
- **FR-003**: 使用者可藉由系統查詢其選定日期與時段的教室借用情況。
- **FR-004**: 系統應提供使用者即時借用、預約借用的功能。
- **FR-005**: 管理員可對每筆借用申請進行核准或拒絕。
- **FR-006**: 管理員可修改借用紀錄狀態與借用人的帳號狀態。
- **FR-007**: 系統紀錄鑰匙交付與歸還情況。
- **FR-008**: 借用人可查看借用歷史紀錄。
- **FRA-001**: 系統應提供校園/系所地圖並標示教室精確位置。
- **FRA-002**: 借用人需輸入學生或教職員證號完成身分驗證。
- **FRA-003**: 系統應整合推播通知，提醒借用狀態變更。
- **FRA-004**: 系統應提供以週課表方式呈現之教室使用狀況圖。
- **FRA-005**: 系統可依違規紀錄限制特定使用者的教室借用資格。

### 非功能需求 (Non-functional Requirements)

- **NFR-001**: 系統應於 **2 秒**內顯示教室使用狀況查詢結果 (對應 FR-003, FRA-004)。
- **NFR-002**: 借用申請送出後，系統應於 **2 秒**內回應是否成功 (對應 FR-004)。
- **NFR-003**: 使用者需完成身份驗證才可提出借用申請 (對應 FR-004)。
- **NFR-004**: 系統介面應能在桌上型電腦及行動裝置正常瀏覽 (RWD)。
- **NFR-005**: 狀態變更或管理員審核時，系統須在 **3 秒**內發送推播通知至使用者裝置 (對應 FRA-003)。
- **NFR-006**: 驗證違規紀錄的 API 處理時間不得超過 **0.5 秒** (對應 FRA-005)。
- **NFR-007**: 地圖圖資與定位圖標必須在 **2 秒**內完全載入 (對應 FRA-001)。
- **NFR-008**: 若地圖伺服器無回應，系統應顯示文字版的「教室位置文字描述」作為備案。
- **NFR-009**: 驗證失敗應明確提示「帳號不存在」或「密碼錯誤」，且不得洩露其他個資 (對應 FRA-002)。
- **NFR-010**: 需支援至少 **100 名**使用者在線操作，高負載下權限切換或頁面跳轉回應不得超過 **5 秒**。
- **NFR-011**: 傳輸全程使用 HTTPS 加密；密碼入庫前須經單向雜湊（如 SHA-256）加密，不得明碼儲存。
- **NFR-012**: 同一教室同一時段，系統**只能核准一筆申請**，需具備防止重複核准的機制（如 DB 交易鎖）。
- **NFR-013**: 僅管理員可執行核准、拒絕及狀態修改；非管理員請求應回傳 HTTP 403 權限錯誤。
- **NFR-014**: 借用人被設為停權後，應於 **5 秒**內生效，且無法再送出新申請。

## 6. 視覺與體驗要求

- **現代校園風格**：整體 UI/UX 需呈現簡潔、專業且直覺的現代化設計。
- **流暢度與響應式**：優先確保 RWD 體驗，操作流程需直覺。若需要動畫效果，可自行評估引入合適的 Svelte 動畫庫（如 `svelte/transition`, `svelte/motion`）。
- **素材與效能**：若使用 [Unsplash](https://unsplash.com/) 等圖片素材，請務必壓縮、最佳化並實作延遲載入（Lazy loading、WebP 格式），以免拖慢網頁載入速度。
- **字體**：推薦使用 [emfont](https://font.emtech.cc/docs) 處理中文 Webfont 服務以提升字體美觀度。

## 7. 測試要求

本系統包含嚴格的效能與並行處理規範，請規劃並撰寫完整的單元測試、整合測試與壓力測試（E2E）。測試必須具體對應以下情境，不要寫沒有實際意義的測試來湊數：

| 測試類別             | 應對應的需求                 | 具體驗證重點與情境                                                                                                                                                      |
| :------------------- | :--------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **高併發與交易鎖**   | NFR-012                      | **(最重要)** 撰寫腳本模擬「多位使用者在同一毫秒內送出『同一教室、同一時段』的借用申請」，驗證資料庫 Transaction Lock 機制是否生效，確保最終系統**只核准唯一一筆**申請。 |
| **效能指標檢驗**     | NFR-001, 002, 006, 010       | 驗證 API 回應時間：<br>1. 查詢狀況 < 2 秒<br>2. 申請回應 < 2 秒<br>3. 違規紀錄驗證 < 0.5 秒<br>4. 100 人在線高負載時，權限切換與頁面跳轉 < 5 秒。                       |
| **狀態機與生命週期** | FR-004~007, FRA-005, NFR-014 | 1. 驗證借用生命週期：`申請中` → `核准/拒絕` → `交付鑰匙` → `歸還`。<br>2. 驗證違規停權機制：設定後 5 秒內生效，且無法送出新申請。                                       |
| **權限與資安**       | NFR-003, 009, 011, 013       | 1. 越權阻擋：一般借用人呼叫管理員 API 回傳 HTTP 403。<br>2. 登入提示：密碼錯誤不得洩露帳號存在與否外的個資。<br>3. 密碼加密：確保 DB 密碼經 SHA-256 處理。              |
| **邊界與備案機制**   | FRA-001, NFR-005, 007, 008   | 1. 地圖降級：地圖逾時(> 2 秒)時 fallback 顯示「文字版位置描述」。<br>2. 推播機制：狀態變更時，推播事件在 3 秒內發出。                                                   |

_註：計時請用 mock timers，資料庫測試需確保每次執行前清空或回滾（Rollback）狀態。效能測試請於 SPEC.md 規劃將使用的工具（如 k6, Locust 等）。_

## 8. `docs/SPEC.md` 內容要求

在正式開始撰寫程式碼之前，請在 `docs/` 資料夾撰寫完整的 `SPEC.md`。

**必要章節**

1. **專案概述 (What to build)**：系統目標與受眾說明。
2. **主要功能與系統行為 (Features & Behavior)**：功能清單與狀態機定義。
3. **系統架構圖與資料流 (System Architecture & Data Flow)**：說明 Svelte, FastAPI 與所選 BaaS 如何協同運作。
4. **資料庫結構 (Database Schema/ERD)**：包含 User, Room, Reservation, Notification 等實體關聯。
5. **API 規格書 (API Endpoints)**：RESTful 路由設計、Request/Response 格式與權限要求。
6. **防呆與邊界條件處理 (Edge Cases)**：特別針對高併發搶借 (NFR-012)、推播失敗、地圖載入失敗等情況的應對策略。
7. **Acceptance Criteria**：對應所有的 FR 與 NFR，必須可驗證。
8. **Non-goals**：明確定義不在本次開發範圍內的功能。

1. **規劃**：利用 Context7 確認需求技術細節，完成 `docs/SPEC.md`。
